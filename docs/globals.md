# Globals

SignalRGB talks to your effect through global variables: one per property, the `on<Prop>Changed` handlers, `engine` and `onCanvasApiEvent`. `srgb-effect-kit` does not wrap them. It types them, so you use them directly with full editor support.

Related: [Configuration](configuration.md) · [Runtime API](runtime-api.md) · [SignalRGB notes](signalrgb-notes.md)

## How the typing works

When Vite loads your config (`pnpm dev` or `pnpm build`), the plugin writes `src/srgb-effect.d.ts`. For the [getting-started](getting-started.md) config it contains:

<!-- prettier-ignore -->
```ts
// Generated by srgb-effect-kit. Do not edit.
/// <reference types="srgb-effect-kit/client" />
declare global {
  var speed: number;
  var mode: "Wave" | "Solid";

  var onSpeedChanged: (() => void) | undefined;
  var onModeChanged: (() => void) | undefined;
}
export {};
```

- Each property becomes a `var`, and so does its change handler. Global `var` declarations are also properties of `window`, so `speed` and `window.speed` are both typed.
- With meters, the file also adds one `number` key per meter to the `SRGBVision` interface, which types `engine.vision`.
- The `/// <reference types="srgb-effect-kit/client" />` line brings SignalRGB's own globals into scope: `engine`, `onCanvasApiEvent`, and the `SRGBBoolean` and `SRGBVision` types.

For this to work:

- **Keep the file inside your tsconfig `include`.** The Vite template's `"include": ["src"]` already covers it. If you change `typesFile`, which is relative to the Vite root, make sure the new path is included too.
- **Commit it.** Without it, `tsc` and your editor do not know the globals until Vite runs once. The plugin writes it only when its content changes.
- **Exclude it from your formatter.** The plugin rewrites it whenever the options change, so a formatter would keep fighting it. For Prettier, add this line to `.prettierignore`:

  ```text
  src/srgb-effect.d.ts
  ```

## Property globals

SignalRGB creates a global for each property, named after its `property` field, and keeps it up to date as the user changes the control. Read it directly wherever you need the current value:

```ts
const ctx = document.querySelector('canvas')!.getContext('2d')!;
ctx.globalAlpha = speed / 100;
```

The type of each global depends on the control type:

| Control type | Global type                  | Example value |
| ------------ | ---------------------------- | ------------- |
| `number`     | `number`                     | `50`          |
| `hue`        | `number`                     | `200`         |
| `boolean`    | `SRGBBoolean` (`'0' \| '1'`) | `'1'`         |
| `color`      | `string`                     | `'#009bde'`   |
| `textfield`  | `string`                     | `'Hello'`     |
| `list`       | union of `values`            | `'Wave'`      |

### Booleans

A `boolean` property arrives as a raw string, typed `SRGBBoolean`, which is `'0' | '1'`. The string `'0'` is truthy, so `if (rainbow)` is always true. Convert it with `parseBoolean()`:

```ts
import { parseBoolean } from 'srgb-effect-kit';

const enabled = parseBoolean(rainbow);
```

The exact raw shape is still to be confirmed on real SignalRGB (see [SignalRGB notes](signalrgb-notes.md#pending-verification-on-real-signalrgb)), so `parseBoolean()` also accepts booleans, numbers and strings such as `'true'` and `'false'`. Using it keeps your code correct whatever the confirmed shape turns out to be.

## Change handlers: `on<Prop>Changed`

For each property, SignalRGB calls a global function named `on` + the property name with its first letter uppercased + `Changed`:

| Property  | Handler            |
| --------- | ------------------ |
| `speed`   | `onSpeedChanged`   |
| `baseHue` | `onBaseHueChanged` |
| `RGBMode` | `onRGBModeChanged` |

SignalRGB calls the handler once when the effect loads, and again every time the user changes the value. The exact order of the load-time calls is [not verified yet](signalrgb-notes.md#pending-verification-on-real-signalrgb). It passes no arguments: read the property global inside the handler. Handlers are optional; define one only when a change needs extra work, such as resetting state or rebuilding a cached value.

Assign the handler to `window`:

```ts
import { hexToHsl } from 'srgb-effect-kit';

// Converting the color once per change is cheaper than once per frame.
let base = hexToHsl(tint);

window.onTintChanged = () => {
  base = hexToHsl(tint);
};
```

A bare assignment, `onTintChanged = () => { … }`, also type-checks and works in the built effect. The build adds a small prelude script that creates every handler global before your code runs, so the assignment does not throw in strict mode. The dev server has no prelude, so prefer `window.`.

### Do not declare handlers at module scope

Your code is bundled as a module, so top-level declarations are local to it and never become globals. SignalRGB cannot see them and never calls them:

```ts
// Never called by SignalRGB:
function onSpeedChanged() {}
const onModeChanged = () => {};
export default function onTintChanged() {}
```

This applies to `function`, `const`, `let` and `var` declarations, exported or not, named after a handler of one of your properties or `onCanvasApiEvent`. The plugin warns when it finds one, in both `pnpm dev` and `pnpm build`:

```text
[srgb-effect] src/main.ts: "onSpeedChanged" is declared at module scope and will never be called by SignalRGB. Assign it instead: window.onSpeedChanged = …
```

## `engine`

SignalRGB injects `engine`, typed `SRGBEngine`. Read it as `engine` or `window.engine`:

```ts
const loudness = engine.audio.level;
```

`engine` exists only inside SignalRGB. In code that must also run in a plain browser, guard it with `globalThis.engine?.…`:

```ts
const level = globalThis.engine?.audio.level ?? -100;
```

The [runtime helpers](runtime-api.md) for audio and screen zones already default to `globalThis.engine` with this guard.

### `engine.audio`

The audio SignalRGB is playing, analyzed continuously.

| Field     | Type                | Range and meaning                                                                          |
| --------- | ------------------- | ------------------------------------------------------------------------------------------ |
| `level`   | `number`            | Loudness in dB, from -100 (silent) to 0 (loud).                                            |
| `width`   | `number`            | Stereo width, 0–1.                                                                         |
| `density` | `number`            | 0 (pure tone) to 1 (white noise).                                                          |
| `freq`    | `ArrayLike<number>` | 200 frequency bands. Values can be negative or garbage; read them with `getFrequencies()`. |

Use [`isSilent()`](runtime-api.md#issilent) to detect silence and [`getFrequencies()`](runtime-api.md#getfrequencies) to get sanitized bands.

### `engine.zone`

The colors of the user's screen, sampled on a 28×20 grid. `hue`, `saturation` and `lightness` are `ArrayLike<number>` with 560 entries each, in row-major order from the top-left: the cell at column `x` and row `y` is at index `y * 28 + x`.

```ts
const x = 3;
const y = 2;
const hue = engine.zone.hue[y * 28 + x];
```

[`getZone(x, y)`](runtime-api.md#getzone) and [`getZones()`](runtime-api.md#getzones) do this indexing for you.

### `engine.vision`

The current value of each [screen meter](configuration.md#meters), keyed by its `meter` name. The generated types declare each one as a `number`:

```ts
const health = engine.vision.health;
```

What the number means depends on the meter type: the fraction of matching pixels (0–1) for `linear` and `area`, 1/0/-1 for `ocr_textmatch`, and the integer read (or -1) for `ocr_numeric`. Meter readings can flicker; [`createMeter()`](runtime-api.md#createmeter) debounces them.

## `onCanvasApiEvent`

Other apps can send events to your effect through SignalRGB's local HTTP API. Assign a handler to receive them:

```ts
let flashUntil = 0;

window.onCanvasApiEvent = ({ sender, event }) => {
  if (sender === 'my-app' && event === 'hit') flashUntil = performance.now() + 200;
};
```

The handler receives a `CanvasApiEvent`, `{ sender: string; event: string }`, built from the query parameters of a `POST` request to `http://localhost:16034/canvas/event`. To try it, run this on the machine running SignalRGB:

```sh
curl -X POST "http://localhost:16034/canvas/event?sender=my-app&event=hit"
```

In Windows PowerShell 5.1, `curl` is an alias for `Invoke-WebRequest`; type `curl.exe` instead.

The module-scope rule above applies to `onCanvasApiEvent` too: assign it, don't declare it.

## Exported types

The types behind these globals are also exported from `srgb-effect-kit`, for annotating your own functions:

```ts
import type { CanvasApiEvent, EngineAudio, SRGBEngine } from 'srgb-effect-kit';

function loudness(audio: EngineAudio): number {
  return audio.level;
}
```

The full list is `SRGBEngine`, `EngineAudio`, `EngineZone`, `CanvasApiEvent` and `SRGBBoolean`. See [Runtime API → Types](runtime-api.md#types).

## Globals in `vite dev`

The devtools drawer that will simulate SignalRGB in the browser is not built yet. Until it is, the dev server defines none of these globals:

- Reading a property global, such as `let current = speed` at the top of a module, throws `ReferenceError: speed is not defined`.
- A bare handler assignment, `onSpeedChanged = …`, throws a `ReferenceError`, because there is no prelude in dev. `window.onSpeedChanged = …` works.
- `engine` is undefined. The runtime helpers treat that as silence and black screen zones.

These all work inside SignalRGB. Test behaviour there, and use the dev server to check the generated markup and catch config and type errors.
